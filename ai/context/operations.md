# lumen — operating contract (for humans and agents)

This is the standing guide to how this product is deployed and operated.
Instance facts (live URLs, workspace, secrets inventory) live in
[deployment.md](deployment.md), regenerated by the baseline's `08-docs`
phase;
this file is the contract that stays true between deployments. It is
written to give an agent with repository read access (e.g. through the
Orun MCP surface) enough context to reason about and operate the system
without any other source.

## What this system is

A multi-tenant SaaS on Cloudflare + Supabase, expressed as an Orun
component-native desired-state repo:

- **`apps/api-edge`** — the single public entry point (Cloudflare Worker).
  Routes to the fleet via service bindings; carries the idempotency KV and
  Hyperdrive (pooled Postgres) bindings.
- **`apps/*-worker`** — bounded-context Workers (identity, membership,
  projects, policy, config, events, webhooks, metering, billing,
  notifications, …). Never public; reached only through the edge.
- **`apps/web-console-next`** — the console UI, Next.js on Workers +
  Static Assets, configured against the edge.
- **`infra/terraform/*`** — data plane: Supabase projects (stage/prod),
  Cloudflare Hyperdrive, idempotency KV. **`infra/db-migrate`** — database
  migrations (plan on PRs, apply on merge).
- **`packages/*`** — shared contracts/SDK packages the apps build on.

Environments: **`stage`** and **`prod`** are fully provisioned and
deployed; **`dev` is verify-only by design** — lanes run, nothing deploys.

## Identity and tenancy

Every remote operation runs against ONE Orun workspace. Resolution order
(most specific wins): `--workspace` flag → `ORUN_WORKSPACE`/`ORUN_ORG` env
→ `intent.yaml` `execution.state.workspace` / `.project` → the repo's
cloud link → `orun workspace use` selection.

- This repo DECLARES its tenancy in `intent.yaml` (`workspace:` +
  `project:` under `execution.state`) — committed, enforced, and what CI
  uses. Do not remove these lines; headless credentials depend on them.
- `orun workspace <ws-id-or-slug>` resolves any workspace's identity
  (works with user sessions and workspace-scoped `ORUN_TOKEN`s alike).
- Project SLUGS in the intent are resolved to `prj_…` ids by the CLI
  (orun ≥ v2.52.4). The CI lane pin in `.github/workflows/ci.yml` must
  stay ≥ v2.56.2 — the floor rose with the phase overlay (v2.56.0) and again
  when a branded tree turned out to refuse its own next phase (v2.56.2).

## How deployment works

1. Merge (or push) to `main`.
2. CI (`.github/workflows/ci.yml`) runs `orun plan --changed` — only
   components whose files changed are planned — then fans each planned
   job into a matrix lane running `orun run --remote-state` with
   credential-free OIDC auth (the exchange resolves this repo's bound
   workspace/project server-side).
3. Terraform state lives in the Orun Cloud HTTP state backend — no local
   state, no cloud-vendor state buckets.
4. **The convergence run is the deployment.** A green run means every
   planned lane applied. Failed lanes are retried with
   `gh run rerun --failed` (the bootstrap's phases automate 3 resumes).

Caveats that matter:

- A push that touches NO component files plans ZERO lanes — that run is
  green but deployed nothing. Never treat "latest run green" as "system
  converged"; assert outcomes (URLs, published secrets) instead. The
  phases' `verify` hooks in `repo-blueprint.yaml` are the pattern to copy.
- GitHub Actions billing exhaustion presents as failing lanes with NO
  logs anywhere; the real message is only in the check-run ANNOTATIONS
  (`gh api repos/<o>/<r>/check-runs/<id>/annotations`).

## Secrets model

- **Brokered provider secrets** (project rung): `CLOUDFLARE_API_TOKEN`,
  `CLOUDFLARE_HYPERDRIVE_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`,
  `SUPABASE_ACCESS_TOKEN`, `SUPABASE_ORG_ID` — pointers minted per-run
  from the workspace's integration connections. No long-lived values at
  rest; nothing to rotate by hand.
- **Job-output secrets** (environment rungs): `WIRING_*`,
  `SUPABASE_PROJECT_REF`, `SUPABASE_DB_URL`, `SUPABASE_DB_PASSWORD` —
  published by the infrastructure terraform; deploy lanes resolve them to
  wire worker bindings (KV ids, Hyperdrive ids, database URLs).
- Inspect by NAME only: `orun secrets list --org <ws> --project` and
  `--env stage|prod`. No tooling in this repo ever prints a secret value,
  and no document in `ai/context/` may contain one.
- Post-bootstrap runtime secrets (OAuth keys, Stripe, …) are seeded with
  `orun secrets set <KEY> --org <ws> --env <env>` — wire-now-seed-later;
  nothing blocks on them.

## Verifying the system (do this, not vibes)

```bash
# the four public surfaces (also recorded, probed, in deployment.md)
curl -s -o /dev/null -w '%{http_code}\n' https://lumen-api-edge-stage.<subdomain>.workers.dev/health
# 200 = deployed and healthy. A 404 here means NOTHING is deployed at that
# name (workers.dev answers 404 for an unclaimed hostname) — not a routing bug.

# published wiring (names only)
orun secrets list --org <ws> --env stage

# workspace readiness (integrations + allow-list + project resolution)
orun integrations list --org <ws> --json && orun cloud check --org <ws>
```

## Common operations

| task | how |
|---|---|
| deploy a change | merge to `main`; watch the run; failed lanes → `gh run rerun --failed` |
| re-verify live state + refresh docs | run the `08-docs` phase (below); idempotent |
| add a runtime secret | `orun secrets set <KEY> --org <ws> --env <env>` |
| resolve workspace identity | `orun workspace <ws-id-or-slug>` |
| check integrations | `orun integrations list --org <ws> --json` |
| custom domain | see [Setting the domain later](#setting-the-domain-later): replace the domain string, create the zone, restore `infra/terraform/cloudflare-domain`'s commented-out `subscribe` block (it ships parked, `subscribe.environments: []`, mid-way to provider v5), merge, then run the `08-docs` phase |
| headless/CI credentials | `ORUN_TOKEN` (workspace-scoped) + `GITHUB_TOKEN` |

The ops phases (docs refresh and the original deployment sequence) all
live in ONE versioned artifact: `repo-blueprint.yaml` in the baseline this
product was born from — the one its Orun Cloud build was started from. Clone
that at the tag the product was built at and select the phase — from
anywhere, with the two tokens above exported:

```bash
git clone --depth 1 --branch <baseline-tag> <baseline-git-url> baseline && cd baseline

orun new --blueprint repo-blueprint.yaml --out <product-checkout> \
  --run-hooks --phase 08-docs --values <values.yaml>     # docs refresh
```

`<values.yaml>` carries this product's identity — at minimum `reponame`,
`productname`, `githuborg` and `orunWorkspace`, which the blueprint validates
before anything runs (and `productdomain` once the product has a domain);
`.rebrand/values.json` in this repository is a complete one. `--run-hooks` is what makes a phase
land and verify rather than just place files; `--status` previews without
writing. Every phase is idempotent — re-running a completed one is a no-op
that re-verifies.

## Setting the domain later

This product answers on workers.dev from its first deploy, and it was built
without a domain. Every place the domain goes carries one string until an
owner sets it — in this repository, `lumen.app` (built without a domain, that
is the reserved placeholder `<reponame>.example.com`, which can never be
anyone's real domain). Nothing that uses the domain was removed; it waits:

| where | what it is |
|---|---|
| `intent.yaml` | `BASE_DOMAIN` (every environment) and `CONSOLE_CUSTOM_DOMAIN` (`stage.lumen.app`, `prod.lumen.app`) — the parameters of the parked `infra/terraform/cloudflare-domain` |
| `infra/terraform/cloudflare-domain` | `baseDomain` in its `component.yaml`, the Terraform variable's default, its README |
| `apps/api-edge/wrangler.template.jsonc` | `CONSOLE_CUSTOM_DOMAIN`, the console origin CORS allows besides the workers.dev one |
| `apps/identity-worker/wrangler.template.jsonc` | `OAUTH_ALLOWED_CONSOLE_ORIGINS`, which lists the workers.dev console too, so sign-in works without a domain |
| `apps/notifications-worker/wrangler.template.jsonc` | `EMAIL_FROM_ADDRESS`, `no-reply@mail.lumen.app` |
| `apps/billing-worker/wrangler.template.jsonc` | `POLAR_SUCCESS_URL`, the fallback return after checkout |
| `tests/api-edge` | the CORS fixtures, which follow the edge's config |

To set it, in one PR:

1. **Replace the string everywhere**, and record the domain as
   `productdomain` in `.rebrand/values.json`, where the docs refresh reads
   it:

   ```bash
   git grep -lF 'lumen.app'          # every file that names it
   git grep -lzF 'lumen.app' | xargs -0 perl -pi -e 's/\Qlumen.app\E/acme.dev/g'   # acme.dev: yours
   ```

2. **Create the zone** in the Cloudflare account the product deploys into
   (dashboard; the platform does not create zones), then restore the
   `subscribe` block `infra/terraform/cloudflare-domain/component.yaml`
   carries commented out, and finish the provider-v5 custom-domain resource
   its comments describe. Until then the console has no custom domain and
   keeps its workers.dev URL.
3. **Verify the mail domain** — `mail.<your domain>` in Cloudflare Email
   Service (DKIM/SPF). The notifications worker sends from
   `no-reply@mail.<your domain>`; until it is verified, sends surface as
   `notification.failed` events and nothing else breaks.
4. **Supabase auth URLs.** This product sets none: sign-in is the identity
   worker's, and `infra/terraform/supabase` names no domain. If you have
   since set Supabase Auth's site URL or redirect URLs in its dashboard,
   point them at the domain too.
5. **The CLI default, if you want it on the domain.** Built without a
   domain, `DEFAULT_API_URL` in `packages/cli/src/brand.ts` is the prod edge
   on workers.dev, `https://lumen-api-edge-prod.<subdomain>.workers.dev`;
   replacing the domain string does not move it. Re-point it once a host on
   your domain routes to the edge.
6. **Merge, then run the docs flow** (the `08-docs` phase, above) once the
   convergence is green and DNS resolves, so `deployment.md` records the
   domain.

## Evolution

Structural changes (new workers, infra components, packages) follow the
same contract that deployed everything here: land the change as a PR,
merge, and the convergence run applies it in dependency order. The ops
phases above re-verify and re-document the system after any change.
